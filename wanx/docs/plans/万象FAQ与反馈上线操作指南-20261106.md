# 万象 FAQ 与反馈上线操作指南

更新：2026-11-06。交接对象：Admin 管理员、Consumer 管理员、DBA、网关运维和万象负责人。适用范围：FAQ 内容管理、个人版/团队版 FAQ 展示及匿名反馈一期。

本次完成本地整合与提交；尚未推送、合入远端 master 或部署服务器。先在完整预发环境按本文执行，验收通过后使用同一候选提交构建生产制品。本文中后台路径均相对于 `nexusaos-admin` 仓库，客户端路径相对于 `centuarai-wanx` 仓库。两个仓库中的本文副本内容一致，修订时应同步。

## 1. 分工与执行顺序

| 角色 | 负责事项 | 需要交回的结果 |
|---|---|---|
| 后台开发/代码负责人 | 将 Admin 集成分支按现有评审流程推送、合并，固定 SHA；同一仓库构建 Admin、Consumer 和管理前端 | 候选 SHA、镜像 digest、前端版本、CI 结果 |
| DBA | 备份、建 FAQ/反馈表、初始化内容锁、精确授权 Consumer 账号、导入菜单 | SQL 执行结果、表结构、授权检查 |
| Consumer 管理员 | 配置 HMAC、Redis、数据库及可信代理；发布 Consumer HTTP/worker；验证公网读写 | release ID、readiness、请求结果 |
| 网关运维 | 对齐旧/新入口路由、16 KiB 请求体限制和转发头；校验再 reload | 脱敏配置差异、两个前缀的验收结果 |
| Admin 管理员 | 发布管理后端/前端；配置真实角色；检查清理任务；安排运营处理人 | 普通账号权限验收、调度任务注册及执行记录 |
| 万象负责人（你） | 确定预发地址、窗口、测试账号、测试文案和验收机器；协调上述人员 | 环境信息、测试数据标记、最终验收确认 |
| 客户端开发/发布人员 | 推送并按流程合并客户端集成分支；固定 SHA；两端连接真实预发；打包、签名和安装升级测试 | 两端验收记录、安装包版本及发布记录 |

顺序：**固定版本/备份 → 建表 → 授权 → 配置 → Consumer 发布 → 网关 → Admin 后端/前端 → 菜单及角色授权 → 全链路预发验收 → 客户端正式打包发布**。菜单可提前导入，角色授权等管理前端就绪后再开放。

Admin 和 Consumer 在同一个源码仓库，但发布制品与状态目录分别管理，必须分别发布；不能只发 Admin 页面。FAQ 已在目标环境上线时，保留原表和菜单，只执行反馈增量，并复核已有结构。

DBA 先确认 `SELECT @@hostname, @@port, VERSION(), CURRENT_USER();` 与目标一致。要求 MySQL 8，支持 `utf8mb4_0900_ai_ci`；FAQ 与反馈业务表位于 `nexus_aos`，后台菜单/角色位于 `nexus_aos_boss`。Admin 与 Consumer 必须访问同一套 FAQ 数据。

备份两个 schema 中相关表、`sys_menu`/`sys_role_menu`、当前运行版本及本次相关 nginx 配置。若首次建表，记录原先不存在的表。使用既有备份工具并确认可恢复，备份含联系方式，应保存在受保护位置。

凭据使用管理员现有的密钥渠道管理；不要把生产 env、私钥、数据库密码或部署 spec 作为本次提交内容。提交中 `.env.prod` 的增量仅有清理开关注释，不能用仓库文件覆盖现场配置。

## 3. DBA 建表和菜单操作

以下为 Linux Bash/MySQL CLI 示例，`ADMIN_REPO` 换成已固定候选的后台源码目录。使用受保护的 MySQL login-path 或现有交互凭据方式；示例 login-path 必须先由 DBA 配置为目标环境。不要在命令行明文写密码，也不要使用忽略错误继续执行的 `--force`。

```bash
export ADMIN_REPO='/实际候选源码目录/nexusaos-admin'
# --login-path=faq-stage 表示 DBA 已配置好的目标环境连接，不是随仓库提供的账号。
mysql --login-path=faq-stage --default-character-set=utf8mb4 \
  < "$ADMIN_REPO/admin-backend/sql/20261105_faq.sql"
mysql --login-path=faq-stage --default-character-set=utf8mb4 \
  < "$ADMIN_REPO/admin-backend/sql/20261106_faq_feedback.sql"
```

首份 SQL 建 `nexus_faq_category`、`nexus_faq_item`、`nexus_faq_content_lock` 并 `INSERT IGNORE` 固定锁行 `id=1`；第二份建 `nexus_faq_feedback`。不需要创建 `sys_job` 行，清理任务由代码注册。

SQL 使用 `CREATE TABLE IF NOT EXISTS`，可以重复执行，但**已有表结构不一致不会自动修正**。若此前手建了半成品表，应比较 `SHOW CREATE TABLE` 与候选 SQL，由 DBA 制定增量修正；不要删表重建已有数据。

```sql
SHOW CREATE TABLE nexus_aos.nexus_faq_category;
SHOW CREATE TABLE nexus_aos.nexus_faq_item;
SELECT id FROM nexus_aos.nexus_faq_content_lock; -- 必须存在且只有固定行 1
SHOW CREATE TABLE nexus_aos.nexus_faq_feedback;
SHOW INDEX FROM nexus_aos.nexus_faq_feedback;
```

检查：FAQ 条目答案为 `MEDIUMTEXT`，分类外键为 `ON DELETE RESTRICT`；反馈的 `idempotency_key` 为 `ascii/ascii_bin` 且有唯一索引 `uk_faq_feedback_idem`；存在 `idx_faq_feedback_created(created_at,id)` 等候选索引。反馈表没有到 FAQ 条目的物理外键，条目删除后旧反馈仍须可读。

### 3.1 Consumer 最小授权：导入与 CALL 是两步

```bash
mysql --login-path=faq-stage --default-character-set=utf8mb4 \
  < "$ADMIN_REPO/admin-backend/sql/20261106_faq_feedback_grant.sql"
```

**上面只创建授权存储过程，不会自动给运行账号授权。** DBA 确认实际账号及匹配的 host 后，在同一目标实例执行：

```sql
-- 将两项占位值替换为实际 user@host；不是把相同用户名的所有 host 都授权。
CALL nexus_aos.grant_faq_feedback_20261106('<consumer_user>', '<consumer_host>');
SHOW GRANTS FOR '<consumer_user>'@'<consumer_host>';
```

该过程需要有检查 `mysql.user`、建过程、授权及 `FLUSH PRIVILEGES` 权限的 DBA 身份。它只新增反馈表 `SELECT, INSERT`，不授予 Consumer `UPDATE, DELETE`。现有运行账号若已有更广权限，此脚本不会自动收回旧授权，应由 DBA 单独审查。

同时确认 Consumer 对 FAQ 分类、条目及读取路径所需内容锁表具有既有读取权限；首次上线 FAQ 时由 DBA 按现有最小授权方案补齐。Admin 运行身份要具备 FAQ CRUD、反馈 `SELECT/UPDATE/DELETE` 及清理所需权限。不要为了省事把 Consumer 换成 root。

从实际 Consumer 主机/容器使用运行账号检查 `CURRENT_USER()`、表读取；再通过 API 真提交一次并同键重提，分别证明 `INSERT` 和幂等回读可用。DBA 账号能查询不能代替运行账号验证。授权操作隐式提交，不能依靠事务 ROLLBACK 撤销。

### 3.2 菜单迁移

```bash
# 首次上线 FAQ 需要此份；已上线且结构一致时复核即可。
mysql --login-path=faq-stage --default-character-set=utf8mb4 \
  < "$ADMIN_REPO/admin-backend/sql/20261105_faq_menu.sql"
mysql --login-path=faq-stage --default-character-set=utf8mb4 \
  < "$ADMIN_REPO/admin-backend/sql/20261106_faq_feedback_menu.sql"
```

两份菜单脚本明确 `USE nexus_aos_boss`，要求恰好一个“业务管理”M 类目录。成功后 FAQ 权限恰好 4 行，反馈权限恰好 3 行：

```sql
SELECT menu_id,parent_id,menu_type,component,perms
FROM nexus_aos_boss.sys_menu
WHERE perms IN ('nexus:faq:list','nexus:faq:add','nexus:faq:edit','nexus:faq:delete',
 'nexus:faq:feedback:query','nexus:faq:feedback:handle','nexus:faq:feedback:delete')
ORDER BY menu_id;
```

若目录重复、权限冲突或过程报错，应停下解决报错，不要绕过守卫插入重复菜单。菜单过程成功后自动删除；失败时可能残留过程，按脚本末尾说明，修正冲突后重新 `CALL` 并 `DROP PROCEDURE`，不要不加判断地整份重跑导致“过程已存在”。菜单 SQL **不自动授予角色**。

## 4. Consumer 配置与发布

Consumer 管理员修改该环境的唯一维护配置源，经既有发布工具生成运行配置：

| 配置 | 操作 |
|---|---|
| DB/Redis | 使用本环境实际运行账号与实例；确认 Redis 可执行原子 Lua 限流 |
| `CONSUMER_FAQ_FEEDBACK_HMAC_KEY` | 安全生成至少 32 字节随机值的十六进制文本，建议 64 个 hex 字符；通过密钥渠道写入；同环境所有 Consumer HTTP 实例保持一致 |
| `FORWARDED_ALLOW_IPS` | 设为实际可信 nginx 对端地址或经过核准的精确范围；不能用 `*` 或为省事信任整个内网 |
| 发布 spec 中 HTTP role 的 `trustedProxies` | Docker 发布器会据此设置容器 `FORWARDED_ALLOW_IPS`，默认 `127.0.0.1`；必须核对容器实际生效值和 Uvicorn 启动参数，env 文件单独改值不保证生效 |
| 既有运行策略 | 保持 `APP_ENV=prod`、`STARTUP_DDL_ENABLED=false`；Consumer worker 继续按既有唯一运行规则执行，不借此次迁移变更架构 |

密钥由管理员在受保护终端生成、保存，不回传聊天或打印进流水线日志。代码对缺失/非法 HMAC、Redis 故障均返回反馈 503；不要删除限流或设置测试默认密钥绕过检查。反馈使用 10 次/分钟/IP；FAQ GET 维持 60 次/分钟及原有降级策略。

从包含本次候选的源码构建 Consumer 镜像，按环境现有流水线发布。当前源码支持 `consumer-service + consumer-worker`，历史环境可能采用拆分角色，以实际 spec 为准；本次不重新执行整套 Consumer 历史迁移。检查所有实际 HTTP/worker 角色的版本、健康、readiness 和 worker 租约，不能只看容器 Running。

已有 Docker 发布流程可参照后台仓库 `consumer-backend/deploy/README-docker.md`、`consumer-backend/deploy/README-codeup.md` 与 `docs/consumer-production-release-runbook.md`。如果该环境使用 `docker_release.py`，使用**候选制品自带工具**和该环境独立 release root：

```bash
python3 "$RELEASE_TOOL" --root "$RELEASE_ROOT" prepare --spec "$RELEASE_SPEC" --release-id "$RELEASE_ID"
python3 "$RELEASE_TOOL" --root "$RELEASE_ROOT" check --release-id "$RELEASE_ID"
# prepare/check 通过后，再执行切换；流水线已执行时不手工重复。
python3 "$RELEASE_TOOL" --root "$RELEASE_ROOT" deploy --release-id "$RELEASE_ID"
python3 "$RELEASE_TOOL" --root "$RELEASE_ROOT" status
```

工具、root、spec、ID 由各管理员填写；Admin 和 Consumer 分开执行。不要把文档中的历史生产流水线当预发触发，不同时用流水线和手工 compose 操作同一环境。

## 5. nginx 两种入口均要验证

网关管理员先保存实际 `nginx -T`，在现场配置中只合入本次增量。参考文件：`consumer-backend/deploy/nginx-public.conf.example` 与 `admin-backend/deploy/docker/cutover/legacy-consumer-map.conf.example`。

| 外部路径 | 方法 | 上游实际路径/要求 |
|---|---|---|
| `/prod-api/app-api/faq`、`/consumer-api/app-api/faq` | GET、OPTIONS | Consumer `/app-api/faq` |
| `/prod-api/app-api/faq/feedback`、`/consumer-api/app-api/faq/feedback` | POST、OPTIONS | Consumer `/app-api/faq/feedback`，16 KiB 请求体限制 |

新入口示例已为反馈配置 `client_max_body_size 16k`；旧入口 map 只决定上游，**不会自动施加大小限制**。使用旧 `/prod-api` 的现场也必须在实际匹配的反馈 location 设置 16k，必要时增加精确匹配 location，正确去掉外部前缀并复用真实 Consumer upstream；不要把限制加到整个 `/prod-api` 影响其他上传接口。

入口覆写 `X-Forwarded-For $remote_addr`、`X-Real-IP $remote_addr`，不能直接追加客户端自带 XFF；若前面还有 CDN/LB，先按既有 real-ip 信任链还原可信来源。Uvicorn 启用 `--proxy-headers` 且仅信任上述对端；应用读写均只取处理后的 `request.client.host`。防火墙维持 Consumer 端口隔离。

核对 location 优先级、方法限制、前缀 rewrite、上游及必需头 `Idempotency-Key`、`X-Wanx-Client` 未被过滤。检查通过后执行 `nginx -t` 再 reload；容器化 nginx 用现场对应方式。两种入口都从外部请求验证，不能仅测容器内 API。

## 6. Admin 发布、角色与日常操作

Admin 管理员从同一后台候选发布管理后端和 `admin-frontend` 构建产物，清理浏览器缓存/重新登录确认新页面生效。既有 Admin 专属调度器必须继续唯一运行：维护配置 `ADMIN_SCHEDULER_ENABLED=true` 与 spec `adminSchedulerActive=true` 一致；`FAQ_FEEDBACK_CLEANUP_ENABLED=true`（默认 true）。保持 Consumer 后台任务由 Consumer worker 负责。

调度器应注册 `internal:nexus_faq_feedback_cleanup`（每天 03:30）与 `internal:nexus_faq_feedback_cleanup_boot`（启动后 5 分钟）。两者宽限 3600 秒，共享进程内互斥锁；按调度器实际时区核对时间，时间配置沿用现有服务。无需手工插 sys_job，也不等待清理结束才认为服务 ready。默认删除所有状态中超过 90 天记录，每批 500、每轮最多 20 批；积压超过 1 万条需观察后续轮次，不宣称一轮全部清空。

“角色管理”中按职责勾选后让用户退出重登：

| 人员 | 页面/权限 |
|---|---|
| FAQ 内容人员 | 业务管理 → 常见问题，C 权限 `nexus:faq:list`；按需加 F 权限 `nexus:faq:add/edit/delete` |
| 反馈查看人员 | 业务管理 → 用户反馈，独立 C 权限 `nexus:faq:feedback:query`；组件 `nexus/faq/feedback/index` |
| 反馈处理人员 | 在反馈查看基础上加 `nexus:faq:feedback:handle` |
| 允许物理删除的人员 | 另加 `nexus:faq:feedback:delete`，按实际职责授予 |

只给反馈菜单不应获得 FAQ 内容权限。必须使用普通真实账号验证角色，超级管理员 `*:*:*` 不能替代权限验收。

运营流程：每天由指定人员进入“用户反馈”，筛选 `pending` → 查看正文、可选联系方式、问题快照和客户端版本 → 改为 `processing` 并填内部备注 → 解决后改 `resolved`，无需处理的改 `ignored`。处理人来自真实登录账号；版本冲突时刷新详情再操作，不覆盖他人修改。删除会物理删除记录。页面不应返回完整 IP HMAC、幂等键或请求指纹。

一期无自动邮件、站内通知或客户端进度查询；如用户留了联系方式，由运营按现有流程联系，不假定系统自动回复。日志不记录完整反馈正文、联系方式、密钥或幂等键。保留期自动清理失败要查 Admin 日志/告警，关闭清理开关后需明确恢复负责人。

## 7. 按顺序验收

先创建有清晰标记的测试分类和问题并上架，正文用非敏感测试内容。测试完按后台正常操作清理测试记录，不直接改正式用户数据。

1. **健康与读取**：检查实际 HTTP 角色 `/healthz`、`/readyz`；两个公网前缀匿名 GET FAQ 都返回预期数据。保存 ETag，以 `If-None-Match` 再 GET 得 304；后台修改公开内容后得新 ETag，下架分类中的编辑不改变公开内容。
2. **匿名提交与幂等**：使用下例对两个实际支持的前缀分别测试，第二个前缀使用新 key；不要带真实联系方式。

```bash
export CONSUMER_BASE='https://实际预发域名/prod-api'
KEY=$(python3 -c 'import uuid; print(uuid.uuid4())')
BODY='{"content":"FAQ预发验收-20261106","contact":""}'
curl -sS -i -X POST "$CONSUMER_BASE/app-api/faq/feedback" \
  -H 'Content-Type: application/json' -H "Idempotency-Key: $KEY" --data-raw "$BODY"
# 原样重发上面的 curl：received=true、duplicate=true，数据库仍只有一条。
```

首次应为 HTTP 200、`code=200`、`success=true`、`data.received=true`、`data.duplicate=false`；原 key 原 body 重发为 duplicate=true；同 key 改内容应 HTTP 409，不增加记录。在后台查到对应反馈，DBA 必要时按测试标记核对唯一一行。

3. **网关与身份**：两个前缀反馈超过 16 KiB 均得 413；伪造 XFF 不改变同对端的限流桶。预发验证无效 Authorization 仍可匿名提交。切勿为了测试放开 Consumer 端口或代理信任范围。
4. **异常与限流（仅独立预发）**：空白正文返回 HTTP 200 + code 601，客户端展示中文提示且保留草稿；缺 key/非法字段 400；同一 IP 一分钟前 10 次受理、第 11 次 429 + Retry-After。故障演练验证 Redis/HMAC/DB 不可用为 503，恢复后原草稿同键可提交；不要停生产 Redis 或修改生产密钥做演练。
5. **真实账号管理**：FAQ 分类/条目 pageSize=1、pageNum=2 和 isActive/categoryId 筛选正确；反馈列表分页、状态、关键字、起止日期正确。反馈查看角色能查详情但不能处理/删除或读取 FAQ 内容；处理记录真实账号、旧 revision 拒绝覆盖。
6. **两端实际客户端**：主进程 `WANX_CONSUMER_URL` 指向上述真实 HTTPS baseURL；进入登录/注册/找回密码、头像设置和升级帮助的 FAQ 入口。确认未登录、未连接盒子可读写；测试正文换行、问题关联、联系方式可选、重复点击、提交中继续编辑、失败保留草稿、成功只清已提交内容。检查后台 personal/team、版本及系统信息；损坏上下文仍受理且全部上下文列为 NULL。后台数据变化无需重新发客户端。
7. **保留期及回归**：预发用专门测试行验证 91 天删除、89 天保留；观察启动/定时清理与互斥。不修改真实用户创建时间。反馈提交前后 FAQ ETag 不变；确认登录、盒子目录和其他现有基础功能正常。

## 8. 客户端发布、回退与交接完成条件

服务器验收通过后，以固定 WANX SHA 按既有打包规范构建、签名并测试安装/升级；本次功能需发布一次客户端新包，旧包不会自行出现新入口。后续 FAQ 内容维护无需再发包。不要从旧布局主工作目录构建，应检出集成后的最新仓库布局。

异常先由发布负责人按现有发布器恢复上一可用 Admin、Consumer、管理前端和相关 nginx 配置，保持版本兼容；保留 FAQ 四张表及已收到反馈，**不 DROP 表回退，不用旧备份覆盖新反馈**。管理前端退回不含新页面时同步隐藏菜单/撤回对应角色授权。需临时暂停清理可将 `FAQ_FEEDBACK_CLEANUP_ENABLED=false` 后按现有流程重启 Admin，并记录恢复时间；该开关不关闭反馈 POST。

GRANT、菜单和 DDL 均需分别评估回退，撤销权限必须只撤本次增量且确认当前版本不再依赖；不能把 `ROLLBACK` 当作撤销 GRANT 的办法。nginx 恢复只回退本次相关差异，保留同期其他团队更新。生产数据不纳入制品回滚。
