## 模型及协议结论

中转站 `https://token.qeeshu.com/v1` 的模型列表返回 HTTP 200，包含 `gpt-6.1-sol`。原配置 `gpt-5.5` 的 Responses 请求返回 HTTP 404、`model_not_found`，本轮改用准确别名 `gpt-6.1-sol`。该结果说明中转站接受这个模型别名，不能独立证明其底层模型身份。

本地 macOS 与 102 Linux 容器使用同一新凭据，保留 TLS 证书验证，均完成以下测试。直接 HTTP 探针显式禁用重定向；原生 Codex 使用标准 provider 配置，未单独验证其重定向策略。

耗时为单次合成测试记录，不代表性能基准或稳定性承诺。函数调用第一轮以有效工具调用为成功条件，最终文本标记在续接回复中验证；没有把第一轮无文本误判为失败。

直接协议请求显式发送 `reasoning.effort=xhigh`、`store=false`，中转站接受这些参数。合成请求回报 reasoning_tokens=0，因此只能确认参数兼容，不能证明实际推理算力等级；`store=false` 也不能独立证明第三方的服务端留存政策。

本次证明新凭据在本机和 102 上兼容 Responses、流式回复、工具续接及真实 Codex app-server。它未经过设备托管模型代理，也没有从原开物正常 PM 界面完成应用生成、采用与导出，因此[原开物验收记录](kaiwu-builder-deployment-box102-20261114.md)中的这三项仍未通过。

下一步需通过正常 Admin 管理接口将新凭据接入 102 的独立托管 provider，仅调整开物默认，保留对话／Starlink 默认和其他盒子配置，再从原开物提交新的 PM 轮次验证。旧失败轮次保留原模型引用，改用新 provider 时，本次验收选择新建轮次以验证新引用；同一 provider 仅轮换密钥时，执行阶段仍会实时解析凭据，不要求一律新建轮次。本轮没有可用的正常 Admin 登录会话；未伪造登录、改数据库密文或绕过托管 provider 校验。
